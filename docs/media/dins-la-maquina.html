Si has vist l'explicació per a tothom, ja saps que la IA proposa i el codi valida. Aquí obrim la caixa: com és exactament un CPE, què escriu el lector, i quins tres controls passa cada proposta abans que el notari la segelli.

Anatomia d'un CPE 2.3 — el carnet, camp a camp

Un CPE és una cadena amb 13 posicions separades per dos punts: un prefix fix i 11 atributs. La majoria de vegades només n'omplim uns quants; la resta queden com a comodins.

cpe:2.3:a:in2code:femanager:5.5.1:*:*:*:*:typo3:*:*
cpe:2.3 — prefix fix: "això és un CPE, versió 2.3 de l'estàndard"
part — aplicació, operatiu (sistema) o hardware
vendor — qui el fa: in2code
product — com es diu: femanager
version — quina versió: 5.5.1
target_sw — sobre quina plataforma corre: typo3 (deduït del "for typo3" del títol)
Els altres cinc atributs (update, edition, language, sw_edition, target_hw, other) segueixen les mateixes regles. Dos valors especials: * = "qualsevol" (no ho sabem o no importa) i - = "no aplica". I una norma d'escriptura estricta: tot en minúscules, espais → _, i els caràcters especials escapats amb \ — Visual C++ s'escriu visual_c\+\+.

El lector una sola pregunta, resposta en JSON

Al lector (un model de llenguatge, normalment un de petit que corre en local) se li ensenyen uns quants exemples resolts i se li passa el títol. Se li demana una sola resposta en JSON amb totes les peces alhora:

// entrada
"Microsoft Visual C++ 2013 Redistributable (x64) - 12.0.30501"
// sortida del lector — això és tot el que pot dir
{
  "vendor": "microsoft",
  "product": "visual c++",
  "version": "2013",
  "update": null,
  "target_sw": null,
  "confidence": 0.93
}
Per què tot alhora i no camp a camp?
Ho vam mesurar (1.000 títols, 5 mides de model): preguntar camp a camp trenca el context — sense veure el vendor, el model no sap on acaba el nom del producte, i el millor resultat per camps queda per sota del pitjor en crida única, costant fins a 6× més.
Per què mai la cadena CPE sencera?
Perquè quan un model genera l'identificador final, s'inventa vendors plausibles amb total convicció (ho vam patir el 2023 amb un LSTM, i els LLMs generalistes d'avui encara ho fan). El JSON limita el lector a dir només el que ha llegit.

I la confidence? És només informativa: es guarda a la fila de resultats, però no decideix res. La classificació final és 100% determinista.

El notari tres controls, cap excepció

1
Bind — muntar la cadena amb normes, no amb gustos
src/cpegen/wfn.py · NISTIR 7695

El codi agafa el JSON i construeix primer un WFN (la forma "lògica" del carnet) i després la cadena: minúscules, espais a _, caràcters especials escapats. El target_sw es dedueix determinísticament del sufix "for X" del títol. Cap decisió creativa: dos runs amb el mateix JSON donen sempre la mateixa cadena.

// del JSON d'abans, el bind produeix:
cpe:2.3:a:microsoft:visual_c\+\+:2013:*:*:*:*:*:*:*
2
Validació ABNF — la gramàtica com a llei
src/cpegen/validator.py · la porta única de sortida

La cadena es contrasta caràcter a caràcter amb la gramàtica oficial ABNF de l'estàndard CPE 2.3. No és una heurística ni un "sembla correcte": és un parser de la norma. Si no valida, la fila surt sense CPE — mai un CPE dubtós.

VÀLID ✓
REBUTJAT ✕
Cas real del primer run: "Controlador de gráficos" — la á no és un caràcter permès per la gramàtica. 81 de 82 títols van passar; aquest, no. El validador fent d'invariant.
3
Diccionari i classificació — existeix, aquest carnet?
src/cpegen/matcher.py · diccionari oficial CPE (snapshot local d'1,77M entrades)

Un CPE ben format encara pot descriure software que el registre oficial no coneix. L'últim control compara el WFN amb el diccionari oficial — igualtat de camps i similitud per distància d'edició — i el classifica amb regles fixes:

ReglaQuè vol dirLectura
M1 · M1AEl carnet (o el parell vendor+producte amb la mateixa versió) existeix al diccionarimatch confirmat — llest per creuar amb CVEs
M1B · M1CVendor i producte coneguts, però versió (o combinació) novacandidat sòlid a CPE nou
M2 · M2B · M3Només quadra una part (vendor conegut i producte nou, o a l'inrevés)candidat a revisar
M4Cap senyal: ni el vendor ni el producte consten al diccionariprobablement soroll d'inventari o software molt minoritari

Mateix WFN + mateixos candidats ⇒ mateixa regla, sigui quin sigui el model que ha llegit el títol. Per això podem comparar models entre ells amb les mateixes vares de mesurar.

El lector pot equivocar-se.
El sistema, no pot mentir.
Una lectura dolenta acaba, com a molt, en un candidat mal classificat — mai en un CPE invàlid ni en un match inventat. I quan la cua difícil s'escala a un model més potent (o a l'agent amb eines), tot el que aquest proposa torna a passar els tres controls: el segell no es delega mai.

Bonus: quan el lector pot fer preguntes

Per als títols més difícils hi ha un mode agent: el lector pot consultar eines abans de respondre — però són eines deterministes, i la seva resposta final segueix sent només una proposta:

bind_and_validate
"Aquestes peces, formen un CPE vàlid?" — prova el bind + ABNF sense comprometre's
search_dictionary
"Què hi ha al diccionari oficial que s'assembli a això?"
classify_match
"Si ho presento així, quina regla M1–M4 em tocaria?"
submit
Presentar la proposta final — que el pipeline revalida i reclassifica sencera, igualment
